Capas del Sistema

Explorá cada capa haciendo click para ver sus responsabilidades y reglas. La arquitectura de capas garantiza que cada componente tiene una única razón de cambio (SRP).

🖥️

Capa de Presentación

Controllers HTTP + WebSocket Gateway. Valida el formato de los datos de entrada. No contiene lógica de negocio.

Componentes: AuthController, HabitController, RecordController, PetController, StatsController, WebSocketGateway

Reglas:
  • Los Controllers solo delegan — no calculan ni deciden
  • Validación de formato con @Valid (Jakarta Bean Validation) (tipos, longitud, regex)
  • Transformación de respuesta con DTOs (ResponseDto.from(domainEntity))
  • Autenticación con Guards (@UseGuards(JwtAuthGuard))

Por qué separar: Si un Controller contiene lógica de negocio, un cambio en las reglas del dominio obliga a modificar la capa HTTP — dos razones de cambio en la misma clase (violación de SRP).
↓
⚙️

Capa de Aplicación

Services que orquestan los casos de uso. Coordinan entidades de dominio, repositorios y servicios externos.

Componentes: AuthService, HabitService, RecordService, PetService, StatsService, NotificationService

Reglas:
  • Los Services conocen el dominio pero NO conocen JPA ni SQL directamente
  • Dependen de interfaces de repositorio, no de implementaciones concretas (DIP)
  • Orquestación de transacciones de negocio (ej: check-in → recalcular mascota → emitir evento)

Por qué separar: Si los Services dependen de JPA/Hibernate directamente, un cambio de ORM requiere modificar la lógica de negocio. Al depender de abstracciones, la infraestructura puede cambiar sin afectar la lógica.
↓
💎

Capa de Dominio

Entidades, Value Objects y reglas de negocio. Independiente de cualquier framework o tecnología.

Componentes: User, Habit, CompletionRecord, Pet (entidades) · WellnessScore (Value Object) · WellnessCalculator, PetStateHandler (abstracciones de dominio)

Reglas:
  • Las entidades pueden tener anotaciones JPA (@Entity, @Column) — son metadatos inertes sin contexto JPA
  • Lo que nunca debe haber: llamadas a repositorios o servicios dentro de métodos de entidad
  • Los Value Objects son inmutables (WellnessScore como Java record)
  • Las reglas de negocio viven en métodos de entidad: validate(), shouldCompleteOn(), addXP()

Por qué separar: El dominio es el conocimiento central del sistema. Si mezcla infraestructura, se vuelve frágil ante cambios tecnológicos y no puede testearse sin base de datos.
↓
🏭

Capa de Infraestructura

Implementaciones concretas: repositorios JPA, BCrypt, Spring STOMP.

Componentes: JpaPetRepository, JpaHabitRepository, JpaUserRepository, JpaRecordRepository · JwtFilter (Spring Security) · HashService (bcrypt)

Reglas:
  • Implementa las interfaces definidas en las capas superiores (DIP)
  • Contiene el código específico de JPA/Hibernate, BCrypt (Spring Security), STOMP server
  • Los repositorios mapean entre entidades de dominio y modelos de JPA (toDomain(), toPersistence())

Por qué separar: Si se cambia de PostgreSQL a otra BD, solo se crea una nueva implementación de repositorio. La lógica de negocio no cambia.
📋 Regla de Dependencias
Las flechas de dependencia solo pueden apuntar hacia las capas internas. La capa de Dominio no puede depender de ninguna otra capa.

🔄 Flujo 1: Check-in de Hábito
El flujo más importante del sistema. Involucra 7 componentes y activa el Observer Pattern para notificar el cambio de estado de la mascota en tiempo real.

🔐 Flujo 2: Autenticación con JWT
El sistema usa dos tokens: access token (15 min, en memoria) y refresh token (7 días, en cookie HttpOnly). El cliente nunca almacena el access token en localStorage.
sequenceDiagram participant FE as React Frontend participant AC as AuthController participant AS as AuthService participant DB as PostgreSQL participant JWT as JwtService FE->>AC: POST /auth/login { email, password } AC->>AS: login(email, password) AS->>DB: findByEmail(email) DB-->>AS: User { hashedPassword, ... } AS->>AS: passwordEncoder.matches(password, hash) Note over AS: BCryptPasswordEncoder strength 10 AS->>JWT: sign({ sub: userId }) → accessToken (15min) AS->>JWT: sign({ sub: userId }) → refreshToken (7 días) AS->>DB: Guardar hash del refreshToken AS-->>AC: { accessToken, refreshToken, user } AC-->>FE: 200 OK (refreshToken en cookie HttpOnly) Note over FE: accessToken en Zustand (memoria)
refreshToken en cookie HttpOnly
No se usa localStorage
Por qué cookie HttpOnly: El refreshToken en localStorage es accesible desde JavaScript y vulnerable a XSS. Una cookie HttpOnly no puede ser leída por scripts del navegador.

Patrones de Diseño GoF

7 patrones aplicados con ejemplos concretos del proyecto. Seleccioná un patrón para ver su diagrama y justificación.

🎯 Strategy Comportamental
Problema: El algoritmo que calcula el bienestar de la mascota puede variar. Modo principiante, modo estricto, modo académico — sin Strategy, cada variante requiere modificar PetService (viola OCP).

Solución: Encapsular cada algoritmo en su propia clase. PetService trabaja con la interfaz WellnessCalculator sin conocer la implementación concreta.
classDiagram class WellnessCalculator { <> +calculate(records, habits, days) WellnessScore } class WeightedAverageStrategy { -applyExponentialWeight(dayIndex) float +calculate(records, habits, days) WellnessScore } class StrictModeStrategy { +calculate(records, habits, days) WellnessScore } class BeginnerModeStrategy { +calculate(records, habits, days) WellnessScore } class PetService { -wellnessCalculator WellnessCalculator +recalcularEstado(userId) Pet } WellnessCalculator <|.. WeightedAverageStrategy : implementa WellnessCalculator <|.. StrictModeStrategy : implementa WellnessCalculator <|.. BeginnerModeStrategy : implementa PetService --> WellnessCalculator : usa
Por qué aquí: Agregar un nuevo modo de cálculo (ej: "Modo Vacaciones" que pausa la degradación) solo requiere crear una nueva clase — sin modificar PetService ni las estrategias existentes.
👁️ Observer Comportamental
Problema: Cuando se completa un check-in, múltiples componentes deben reaccionar: PetService, StatsService, NotificationService. Si RecordService los llama directamente, el acoplamiento es insostenible.

Solución: RecordService emite un evento record.completed. Los interesados se suscriben con @OnEvent. El emisor no conoce a los suscriptores.
classDiagram class EventEmitter { <> +emit(event, payload) void +on(event, handler) void } class RecordService { -eventEmitter EventEmitter +checkIn(userId, habitId) CompletionRecord } class PetService { +onRecordCompleted(payload) void } class StatsService { +onRecordCompleted(payload) void } class NotificationService { +onPetStateChanged(payload) void } RecordService --> EventEmitter : emite record.completed PetService ..> EventEmitter : suscrito StatsService ..> EventEmitter : suscrito NotificationService ..> EventEmitter : suscrito
Por qué aquí: Sin Observer, RecordService dependería directamente de PetService, StatsService y NotificationService — 3 dependencias acopladas. Con Observer, tiene una sola dependencia (EventEmitter) y es extensible sin modificación.
🔀 State Comportamental
Problema: La mascota tiene 5 estados con comportamientos distintos (animación, mensaje, multiplicador XP, alertas). Sin State, hay bloques switch en múltiples lugares que crecen con cada nuevo estado.

Solución: Cada estado es una clase que encapsula su propio comportamiento. Pet delega las decisiones de comportamiento a su objeto estado actual.
classDiagram class PetStateHandler { <> +getMessage() string +getAnimationClass() string +shouldAlert() bool +getXpMultiplier() float } class CriticalState { +getMessage() string +getAnimationClass() string +shouldAlert() bool +getXpMultiplier() float } class PoorState class NeutralState class GoodState class ExcellentState { +getMessage() string +getAnimationClass() string +shouldAlert() bool +getXpMultiplier() float } class Pet { -stateHandler PetStateHandler +getMessage() string +getAnimationClass() string +applyXpGain(base) int } PetStateHandler <|-- CriticalState PetStateHandler <|-- PoorState PetStateHandler <|-- NeutralState PetStateHandler <|-- GoodState PetStateHandler <|-- ExcellentState Pet --> PetStateHandler : delega comportamiento
🗃️ Repository Arquitectural
Problema: Si PetService usa EntityManager o JpaRepository directamente, un cambio de ORM requiere modificar la lógica de negocio. Además, los tests unitarios no pueden correr sin base de datos.

Solución: Interfaz PetRepository (abstracción). En producción: JpaPetRepository extends JpaRepository. En tests: InMemoryPetRepository.
classDiagram class PetRepository { <> +findByUserId(userId) Pet +save(pet) Pet } class JpaPetRepository { -prisma EntityManager +findByUserId(userId) Pet +save(pet) Pet -toDomain(data) Pet -toPersistence(pet) JpaEntity } class InMemoryPetRepository { -storage Map +findByUserId(userId) Pet +save(pet) Pet } class PetService { -petRepository PetRepository +recalcularEstado(userId) Pet } PetRepository <|-- JpaPetRepository : producción PetRepository <|-- InMemoryPetRepository : tests PetService --> PetRepository : depende de abstracción
Por qué aquí: Los tests unitarios de PetService corren sin base de datos real usando InMemoryPetRepository. Son rápidos, predecibles y no requieren Docker.
🏭 Factory Method Creacional
Problema: Hay diferentes tipos de hábitos (frecuencia semanal, meta única). HabitService no debería conocer los detalles de construcción de cada tipo.

Solución: Cada tipo de hábito tiene su propia Factory. El registry de factories permite agregar nuevos tipos sin modificar código existente.
classDiagram class HabitFactory { <> +createHabit(dto, userId) Habit #buildHabit(dto, userId) Habit } class FrequencyHabitFactory { +createHabit(dto, userId) FrequencyHabit #buildHabit(dto, userId) FrequencyHabit -suggestDays(freq) int[] } class OneTimeHabitFactory { +createHabit(dto, userId) OneTimeHabit #buildHabit(dto, userId) OneTimeHabit } class HabitFactoryRegistry { -factories Map +getFactory(type) HabitFactory } class Habit { <> +shouldCompleteOn(day) bool +getXpReward() int } HabitFactory <|-- FrequencyHabitFactory HabitFactory <|-- OneTimeHabitFactory HabitFactoryRegistry --> HabitFactory FrequencyHabitFactory ..> Habit OneTimeHabitFactory ..> Habit
🎁 Decorator Estructural
Problema: Los hábitos pueden tener bonus combinables: "hábito del día" (2x XP) + "racha activa" (XP extra). Con herencia, 2 comportamientos generan 4 combinaciones; 3 generan 8 (explosión combinatoria).

Solución: Cada comportamiento adicional es un Decorator que envuelve al hábito y agrega su lógica encima.

ConcreteHabit HabitComponent <|.. HabitDecorator HabitDecorator <|-- DailyFeaturedDecorator HabitDecorator <|-- StreakBonusDecorator HabitDecorator --> HabitComponent : wraps
🚪 Facade Estructural
Problema: El proceso de check-in involucra múltiples pasos: verificar hábito, crear registro, recalcular mascota, calcular XP. Si el controller orquesta todo esto, tiene demasiadas responsabilidades.

Solución: CheckInFacade expone una interfaz simple. El controller solo llama a performCheckIn().
flowchart LR RC["RecordController"] -->|"performCheckIn()"| CF["CheckInFacade"] CF --> HR["HabitReader\n(verificar ownership)"] CF --> RS["RecordService\n(crear registro)"] CF --> PS["PetService\n(obtener estado)"] style CF fill:#1e2535,stroke:#3b82f6,stroke-width:2px style RC fill:#242838,stroke:#6366f1
Por qué aquí: El Controller queda con una sola línea de lógica: llamar a la Facade. Si el proceso de check-in cambia (ej: se agrega gamificación), solo cambia la Facade, no el Controller.

S Single Responsibility
Una clase debe tener una única razón para cambiar.
ClaseÚnica responsabilidad
WeightedAverageStrategyCalcular bienestar con promedio ponderado
XpCalculatorCalcular XP ganado y nivel resultante
PetServiceOrquestar la actualización de la mascota
PetRepositoryPersistir y recuperar la entidad Pet
O Open/Closed
Abierto para extensión, cerrado para modificación.
Punto de extensión: WellnessCalculator
Para agregar "Modo Vacaciones" que pausa la degradación, se crea VacationModeStrategy implements WellnessCalculator.

PetService no cambia. WeightedAverageStrategy no cambia.
L Liskov Substitution
Las subclases deben poder reemplazar a la clase base sin romper el sistema.
WellnessCalculator.calculate(records, habits, days) funciona igual con una lista mezclada de FrequencyHabit y OneTimeHabit. Agregar ChallengeHabit no rompe el cálculo — si respeta el contrato de Habit.
I Interface Segregation
Los clientes no deben depender de interfaces que no usan.
PetService solo necesita leer hábitos → depende de HabitReader (2 métodos).

Si cambia HabitStatsReader (métodos de estadísticas complejas), PetService no es afectado porque no depende de esa interfaz.
D Dependency Inversion — Diagrama
Módulos de alto nivel (PetService) no dependen de módulos de bajo nivel (JpaPetRepository). Ambos dependen de la abstracción (PetRepository).
