Resumen ejecutivo

HabitPet es una aplicación que conecta el seguimiento de hábitos saludables con el concepto de mascota virtual al estilo Tamagotchi. La premisa central es que vincular el progreso a una entidad con la que el usuario desarrolla un vínculo emocional aumenta la retención frente a apps de tracking tradicionales con métricas abstractas.

Stack técnico

Spring Boot 3.3 Java 21 Spring Data JPA Spring Security + JWT Spring WebSocket + STOMP PostgreSQL 16 Flyway React 18 + Vite TypeScript Zustand TailwindCSS Docker Compose
Contexto de la defensa
El énfasis de esta documentación no está en el volumen de funcionalidades sino en la correcta aplicación de principios de diseño, la justificación de cada decisión arquitectónica y la documentación explícita de los trade-offs aceptados por ser un proyecto universitario.

Arquitectura

Decisión: capas horizontales en lugar de paquetes DDD por dominio

Lo que teníamos planificado: paquetes organizados por bounded context (auth/, habit/, record/, etc.), cada uno con sus subcarpetas domain/, repository/, service/.

Lo que se implementó: capas horizontales planas: models/, repositories/, services/, controllers/, etc.

Justificación: Para un MVP universitario con ~10 entidades, la estructura DDD agrega complejidad sin beneficio real. Las capas horizontales son más intuitivas, más fáciles de navegar y demuestran igualmente la separación de responsabilidades. El DDD escala cuando los bounded contexts son verdaderamente independientes y hay equipos separados — acá no es el caso.

Decisión: Modelo de dominio anémico (sin lógica en entidades)

Las entidades JPA son data holders puros: getters, setters, timestamps. Toda la lógica de negocio vive en los services.

Justificación: Facilita el testing (servicios testeables con mocks simples), evita el acoplamiento de entidades a Spring (no necesitan ApplicationContext), y mantiene la separación entre el modelo de datos y el modelo de negocio. El modelo rico (Rich Domain Model) tiene valor cuando las reglas de negocio son complejas y viven naturalmente en la entidad — acá la complejidad vive en el cálculo de bienestar, que se implementó correctamente con Strategy.

Nota para la defensa
Esta es una decisión deliberada y justificada, no un olvido. Se discutió y se eligió conscientemente.

Pattern: Strategy

Patrón GoFWellnessCalculator

Problema: el algoritmo de cálculo de bienestar de la mascota podía variar. En el MVP se usa promedio ponderado exponencial, pero podría cambiar a promedio lineal, scoring por racha, etc.

Solución: encapsular el algoritmo detrás de una interfaz. WellnessService no sabe qué implementación está usando — recibe un WellnessCalculator por constructor (Spring lo inyecta).

// Interfaz Strategy — cerrada para modificación
public interface WellnessCalculator {
    WellnessScore calculate(
        List<Habit> activeHabits,
        List<CompletionRecord> recentRecords,
        LocalDate referenceDate
    );
}

// Implementación concreta: exponential weighted average
@Component
public class ExponentialWeightedWellnessCalculator implements WellnessCalculator {
    private static final double DECAY = Math.log(2); // peso se reduce a la mitad cada día
    private static final int WINDOW_DAYS = 7;

    @Override
    public WellnessScore calculate(...) {
        // weight(day) = e^(-ln(2) * day)
        // día 0 (hoy) = peso 1.0, día 6 = peso 0.094
    }
}

// WellnessService no sabe qué implementación usa
@Service
public class WellnessService {
    private final WellnessCalculator wellnessCalculator; // depende de la abstracción
}
¿Cuándo aplicar Strategy?
Cuando hay un algoritmo que puede variar independientemente de quien lo usa. Acá el algoritmo de bienestar es el candidato natural: podría cambiar sin tocar WellnessService ni ningún otro componente.
Algoritmo del cálculo de bienestar

Para cada uno de los últimos 7 días:

  • weight(día) = e-ln(2) × día (día 0 = hoy, peso máximo)
  • dailyRate = check-ins ese día / total hábitos activos
  • weightedSum += weight × dailyRate

score final = (weightedSum / totalWeight) × 100

Ejemplo: 1 hábito, check-ins en días 0, 1, 3 → score ≈ 82% (GOOD). Con promedio simple sería 3/7 = 43% (NEUTRAL). La diferencia es que los check-ins recientes (hoy y ayer) tienen mucho más peso.

Pattern: Observer

Patrón GoFSpring Application Events

Problema: RecordService guarda el check-in. ¿Cómo notifica a WellnessService sin acoplarse directamente a él?

Solución: Spring Events. RecordService publica un evento; WellnessService lo escucha con @EventListener. Ninguno sabe del otro.

// El evento — simple record de Java 21
public record CheckInCompletedEvent(String userId, LocalDate date) {}

// Publisher: RecordService solo sabe publicar el evento
@Service
public class RecordService {
    private final ApplicationEventPublisher eventPublisher;

    public RecordResponse checkIn(String userId, ...) {
        // ... guardar check-in ...
        eventPublisher.publishEvent(new CheckInCompletedEvent(userId, today));
        // RecordService NO conoce WellnessService
    }
}

// Subscriber: WellnessService escucha sin que nadie lo llame directamente
@Service
public class WellnessService {
    @EventListener
    public void onCheckInCompleted(CheckInCompletedEvent event) {
        // recalcula wellness y actualiza mascota
    }
}
Ventaja del desacoplamiento
Si mañana queremos mandar también una notificación push cuando alguien hace check-in, creamos un NotificationService con @EventListener(CheckInCompletedEvent.class) y no tocamos RecordService.
Nota técnica
Por defecto, Spring Events son síncronos — el evento se procesa en el mismo thread y transacción. Para producción, se usaría @Async para no bloquear la respuesta HTTP mientras se calcula el bienestar.

Pattern: Facade

Patrón GoFWellnessService como Facade

Problema: el flujo post-check-in involucra múltiples servicios (HabitService, RecordService, WellnessCalculator, PetService, PetWebSocketGateway). Coordinar todo eso en el RecordController o en cada servicio individualmente crearía acoplamiento.

Solución: WellnessService actúa como Facade. Conoce todos los componentes necesarios, los coordina, y ningún otro componente necesita saber de esta orquestación.

@Service
public class WellnessService {
    // Conoce todos los componentes — nadie más necesita hacerlo
    private final HabitService habitService;
    private final RecordService recordService;
    private final WellnessCalculator wellnessCalculator;
    private final PetService petService;
    private final PetWebSocketGateway petWebSocketGateway;

    @EventListener
    public void onCheckInCompleted(CheckInCompletedEvent event) {
        List<Habit> habits = habitService.listActiveHabits(event.userId());
        List<CompletionRecord> records = recordService.getRecentRecords(event.userId(), 7);
        WellnessScore score = wellnessCalculator.calculate(habits, records, event.date());
        Pet pet = petService.updateWellness(event.userId(), score);
        petWebSocketGateway.notifyPetUpdate(event.userId(), pet, score);
    }
}

Cada servicio mantiene su propia responsabilidad. WellnessService es el único que sabe cómo ensamblarlos. Los controllers y otros servicios solo interactúan con servicios específicos, no con este flujo complejo.

Pattern: Repository

Patrón GoFSpring Data JPA

Los repositorios abstraen el acceso a datos. Los servicios nunca construyen queries directamente — trabajan con interfaces tipadas que Spring implementa automáticamente.

// Los servicios dependen de interfaces, no de SQL
public interface CompletionRecordRepository extends JpaRepository<CompletionRecord, String> {

    // Spring genera la query: SELECT * FROM completion_records WHERE habit_id=? AND date=?
    boolean existsByHabitIdAndDate(String habitId, LocalDate date);

    // Para la ventana de wellness: query JPQL explícita por legibilidad
    @Query("SELECT r FROM CompletionRecord r WHERE r.userId=:userId AND r.date>=:from AND r.date<=:to ORDER BY r.date DESC")
    List<CompletionRecord> findByUserIdInDateRange(...);
}
Decisión de diseño: userId desnormalizado en CompletionRecord
CompletionRecord tiene userId como campo directo (sin FK JPA a User). Esto permite un índice compuesto (user_id, date) que soporta eficientemente la query de bienestar sin necesidad de JOIN. Documentado como decisión de performance intencional.

SOLID: Open/Closed Principle

SOLID — OCPJerarquía de excepciones

El principio: las clases deben estar abiertas para extensión pero cerradas para modificación.

Dónde se aplica: el manejo de excepciones. GlobalExceptionHandler captura AppException (la clase base) y nunca se modifica aunque agreguemos nuevos tipos de error.

// Clase base — cerrada para modificación
public abstract class AppException extends RuntimeException {
    private final HttpStatus status;
    private final String code;
    private final String userMessage;
    private final String logMessage; // opcional
}

// Extensión sin tocar nada existente
public class ResourceNotFoundException extends AppException { ... }
public class ResourceAlreadyExistsException extends AppException { ... }
public class InvalidCredentialsException extends AppException { ... }
public class DuplicateCheckInException extends AppException { ... }
public class LimitExceededException extends AppException { ... }

// El handler captura la base — NUNCA se modifica
@RestControllerAdvice
public class GlobalExceptionHandler {
    @ExceptionHandler(AppException.class)
    public ResponseEntity<ErrorResponse> handle(AppException ex) {
        // Funciona para todas las subclases actuales y futuras
    }
}
OCP + Strategy juntos
WellnessCalculator también demuestra OCP: para cambiar el algoritmo, se crea una nueva clase que implementa la interfaz. WellnessService no se modifica.

SOLID: Dependency Inversion Principle

SOLID — DIPDepender de abstracciones

El principio: los módulos de alto nivel no deben depender de módulos de bajo nivel. Ambos deben depender de abstracciones.

Aplicado: WellnessService

// Depende de la interfaz, no de la implementación
private final WellnessCalculator wellnessCalculator;
// Spring inyecta ExponentialWeighted...
// sin que WellnessService lo sepa

Aplicado: Constructor injection

// Sin @Autowired en campos — siempre
// inyección por constructor
@RequiredArgsConstructor
public class HabitService {
    private final HabitRepository repo;
    private final UserRepository userRepo;
}
Por qué constructor injection
La inyección por campo (@Autowired) hace las dependencias implícitas y dificulta el testing (no se puede crear el objeto sin un contexto de Spring). La inyección por constructor hace las dependencias explícitas, permite tests con simples new Service(mockRepo), y garantiza que el objeto es inmutable después de crearse.

Anotación compuesta + DIP en Spring Boot

SOLID — DIP@SpringBootApplication como anotación compuesta

@SpringBootApplication no es una sola anotación — es una meta-anotación que compone tres responsabilidades en una sola declaración:

// Lo que @SpringBootApplication realmente es:
@Configuration         // esta clase define beans de Spring
@EnableAutoConfiguration // activa la auto-configuración de Spring Boot
@ComponentScan          // escanea paquetes en busca de @Component, @Service, etc.

// En el proyecto — con exclusión explícita:
@SpringBootApplication(exclude = {UserDetailsServiceAutoConfiguration.class})
public class HabitPetApplication { ... }
SOLID — DIPPor qué se excluye UserDetailsServiceAutoConfiguration

Spring Security, al detectarse en el classpath, auto-configura un UserDetailsService por defecto que genera una contraseña random al arrancar. Esto sirve para aplicaciones que usan el sistema de login de formularios de Spring.

En HabitPet la autenticación es completamente nuestra — el JwtAuthFilter valida el token JWT y carga el usuario manualmente en el SecurityContext, sin depender del mecanismo de Spring. No necesitamos ni queremos ese servicio por defecto.

Al excluirlo, aplicamos DIP: en lugar de depender de la implementación de autenticación que Spring Boot provee por convención, definimos la nuestra propia. Le decimos explícitamente a Spring: "no necesito tu UserDetailsService, tengo mi propio mecanismo".

Sin la exclusión
Al arrancar el backend aparece en los logs: Using generated security password: 4a142bf7-... junto con una advertencia de seguridad. Con la exclusión ese mensaje desaparece y el sistema queda limpio.
Concepto: Convention over Configuration
Spring Boot usa el principio de "convención sobre configuración" — por defecto hace muchas cosas automáticamente. El exclude es la forma de decirle "en este punto específico, quiero mi propia configuración en lugar de la convención".

SOLID: LSP + ISP

SOLID — LSPLiskov Substitution Principle

Todas las subclases de AppException son sustituibles por la clase base sin alterar el comportamiento del GlobalExceptionHandler. El handler llama ex.getStatus(), ex.getCode(), ex.getUserMessage() — métodos definidos en la base y correctamente implementados por todas las subclases.

SOLID — ISPInterface Segregation Principle

WellnessCalculator tiene un solo método. UserRepository expone solo findByEmail y existsByEmail — no expone operaciones de otros dominios. Las interfaces son pequeñas y cohesivas; ningún cliente se ve forzado a depender de métodos que no usa.

Principios GRASP

GRASPAlta Cohesión

Cada servicio tiene responsabilidades altamente relacionadas entre sí. HabitService solo sabe de hábitos. RecordService solo sabe de check-ins. Esta cohesión alta se mantiene gracias a las reglas de comunicación entre capas: cada servicio accede solo a su propio repositorio.

GRASPPolimorfismo

El GlobalExceptionHandler llama ex.getStatus() sobre cualquier AppException sin saber qué subclase es en tiempo de compilación. Java resuelve el método correcto en runtime según el tipo real del objeto. Esto es polimorfismo GRASP en acción: el comportamiento varía según el tipo, sin conditionals (if instanceof).

// Sin polimorfismo (mal):
if (ex instanceof ResourceNotFoundException) { status = 404; }
else if (ex instanceof DuplicateCheckInException) { status = 409; }

// Con polimorfismo (bien) — el tipo sabe su propio status:
HttpStatus status = ex.getStatus(); // funciona para todas las subclases
GRASPInformation Expert

WellnessScore (value object) tiene el método toState() que convierte el score numérico a PetState. ¿Por qué está en WellnessScore y no en PetService? Porque WellnessScore es el experto en información sobre el score — es quien tiene los umbrales y sabe qué significa cada rango.

public record WellnessScore(double value) {
    public PetState toState() {
        if (value <= 20.0) return PetState.CRITICAL;
        if (value <= 40.0) return PetState.POOR;
        if (value <= 60.0) return PetState.NEUTRAL;
        if (value <= 80.0) return PetState.GOOD;
        return PetState.EXCELLENT;
    }
}

Patrones que se decidió NO aplicar

Tan importante como aplicar un patrón correctamente es justificar cuándo no aplicarlo.

No aplicadoActive Record en entidades

Idea propuesta: que las entidades tuvieran métodos habit.save() o habit.delete() para operar sobre sí mismas.

Por qué se rechazó: viola SRP (la entidad tendría responsabilidad de persistencia además de representar datos) y DIP (la entidad dependería directamente de infraestructura — Spring ApplicationContext o repositorios). Hace el testing más complejo. El patrón Active Record es válido en frameworks como Rails donde el ORM está diseñado para eso; en JPA/Spring, la separación entity/repository es el enfoque correcto.

No aplicadoSingleton explícito

Todos los beans de Spring son singletons por defecto. No se necesita implementar el patrón manualmente — Spring lo gestiona.

No aplicadoDecorator

Se consideró para agregar multiplicadores de XP según el estado de la mascota (ej: EXCELLENT da +20% XP). Se descartó porque la lógica es simple y no hay suficientes variaciones que justifiquen la indirección. Se implementó como lógica directa en PetService.

No aplicadoChain of Responsibility

Considerado para el pipeline de validación en check-ins (¿el hábito existe? ¿pertenece al usuario? ¿está activo? ¿ya hizo check-in hoy?). Descartado porque son 4 validaciones secuenciales simples — una cadena de handlers sería sobrengineering sin beneficio real de mantenibilidad.

No aplicadoLógica de negocio en entidades (Rich Domain Model)

Se debatió si métodos como pet.agregarXP() o habit.archivar() debían vivir en las entidades. Se eligió el modelo anémico porque: (1) el testing es más limpio con servicios testeables por mocks, (2) las reglas de negocio más complejas (cálculo de wellness) no pertenecen naturalmente a ninguna entidad, y (3) las entidades JPA tienen ciclo de vida gestionado por Hibernate lo que puede crear comportamientos sorpresivos con lógica en métodos de instancia.

Trade-offs aceptados

Decisiones donde se eligió la opción más simple sabiendo sus limitaciones, por tratarse de un proyecto universitario.

Trade-offJWT en localStorage

Implementado: el token JWT se guarda en localStorage del browser.

Riesgo aceptado: expuesto a ataques XSS — si un script malicioso corre en el browser, puede leer el token.

Alternativa correcta para producción: HttpOnly cookies manejadas por el servidor — el token nunca es accesible desde JavaScript.

Por qué se aceptó: simplifica enormemente el frontend para la demo universitaria. Documentado con comentario en el código.

Trade-offWebSocket con topic público por usuario

Implementado: /topic/pet/{userId} — cualquier cliente que conozca el userId puede suscribirse.

Alternativa correcta: convertAndSendToUser() con autenticación WebSocket (ChannelInterceptor que valida el JWT en el frame STOMP CONNECT).

Por qué se aceptó: la autenticación de WebSocket requiere configuración adicional significativa que no agrega valor pedagógico al proyecto. El principio de WebSocket en tiempo real se demuestra igualmente. Documentado con comentario en el código y en este reporte.

Trade-offHabitCategory como enum hardcodeado

Implementado: enum HabitCategory { HEALTH, STUDY, SPORT, WELLNESS, NUTRITION }.

Alternativa escalable: tabla en base de datos o servicio de configuración — permite agregar/modificar categorías sin redespliegue.

Por qué se aceptó: MVP universitario con categorías estables. Documentado con comentario en el enum.

Trade-off@CreationTimestamp/@UpdateTimestamp en lugar de @PrePersist

Problema técnico encontrado: cuando se asigna el ID manualmente antes de llamar a repository.save(), Spring Data JPA llama merge() en lugar de persist(), y @PrePersist no dispara.

Solución correcta a largo plazo: implementar Persistable<String> en las entidades para que Spring Data siempre llame persist() para entidades nuevas.

Solución implementada: @CreationTimestamp y @UpdateTimestamp de Hibernate, que funcionan independientemente del tipo de operación JPA.

Trade-offFlyway validate-on-migrate: false en perfil docker

Por qué existe: el script V2 fue modificado post-aplicación (corrección del hash BCrypt de los usuarios seed), lo que invalidó el checksum almacenado por Flyway.

Práctica correcta: nunca modificar un script ya aplicado — crear un V3 de corrección. En este proyecto se hizo esto (V3__fix_seed_passwords.sql) pero el checksum de V2 quedó en estado inconsistente.

Solución: validate-on-migrate: false en el perfil docker con comentario documentando el motivo. En producción se ejecutaría flyway repair.

Filosofía de testing
Se testeó comportamiento, no implementación. Los tests de ExponentialWeightedWellnessCalculator no mockean nada — validan el algoritmo directamente. Los tests de servicios validan las interacciones entre componentes con mocks de sus dependencias.
Decisión: no tests de integración con base de datos

Los tests unitarios con mocks son rápidos y suficientes para validar la lógica de negocio en este MVP. Los tests de integración con base de datos real (usando @DataJpaTest + Testcontainers) son el siguiente paso lógico pero están fuera del alcance de esta entrega.
